# Mercury v0.2.2 Strict Release Recovery Design

**Date:** 2026-07-17

**Status:** Approved architecture, pending written-spec review

**Target branch:** `mercury-v0.2.2-strict-release` from
`45e771c9d8d7213bc06141d205b852f079adbcfa`

**Target release:** `v0.2.2`

## Summary

Mercury v0.2.2 repairs the release architecture without moving or deleting the
existing immutable `v0.2.1` tag. A new public repository named
`natthaphonchop2-creator/mercury-release-control-v2` becomes the trusted control
plane for provider inspection, history-free staging, attestation, and final
GitHub publication. Mercury remains the product and candidate repository; it
never receives Render, Supabase, FlowAccount, or cross-repository publication
credentials.

The release-control repository is completed, protected, independently reviewed,
and merged before its exact commit SHA is inserted into Mercury. The trusted
control workflow creates the staging repository itself from a canonical filtered
public tree. Mercury independently reconstructs that same tree and verifies the
digest before it builds release artifacts. The final annotated tag and GitHub
Release are created only after both repositories, Render, Supabase, the public
MCP, the plugin install path, and the artifact handoff pass their exact gates.

## Why v0.2.2 Is Required

The v0.2.1 product commit, public repository, hosted MCP, and tag are usable, but
the strict release pipeline cannot complete as written:

1. `v0.2.1` was tagged before the release-control implementation SHA replaced
   the all-zero `RELEASE_CONTROL_PIN`.
2. The v0.2.1 trusted inspector hashes the complete 387-file Git archive while
   the Mercury release builder hashes the 352-file filtered public tree. Their
   digests cannot match.
3. The v0.2.1 staging repository was not created before the attestation workflow
   required it.
4. The original release-control verifier requires critical files to remain
   byte-identical forever, so the repository has no protected upgrade path for
   correcting these defects.

The existing `v0.2.1` tag remains immutable evidence. It is not repointed,
deleted, or presented as having passed the incomplete strict attestation.

## Goals

1. Produce a strict, immutable `v0.2.2` GitHub Release from the exact reviewed
   Mercury `main` commit.
2. Keep every production/provider secret outside Mercury code, workflows,
   artifacts, logs, RAG, MCP output, and Git history.
3. Remove the release-control pin and staging bootstrap cycles.
4. Use one canonical public-tree definition on both sides of the trust boundary.
5. Preserve the existing one-plugin, one-local-MCP product shape and the hosted
   MCP's read-only Cloud Brain behavior.
6. Make release-control code upgradeable through protected review without ever
   executing pull-request code in a privileged job.
7. Fail before tag creation when any identity, digest, provider, database,
   scanner, artifact, or install gate is missing or inconsistent.

## Non-Goals

- v0.2.2 does not add new ERP actions or change production ERP write policy.
- v0.2.2 does not move, delete, or recreate `v0.2.1`.
- Mercury does not become a web application or a local LLM.
- Render and Supabase do not receive ERP credentials or raw accounting payloads.
- Candidate workflows do not receive production/provider secrets.
- The release process does not claim that secret scanning is mathematical proof
  that no undiscovered secret exists outside the declared corpus.

## Repository Roles

### Mercury Tools

`natthaphonchop2-creator/mercury-tools` owns product source, package metadata,
plugin metadata, the local stdio MCP, the hosted read-only MCP, ERP catalogs,
accounting knowledge, tests, and secretless artifact construction. Its release
workflow accepts only a bounded sanitized attestation and exact artifact
identities from release-control.

### Release Control v2

`natthaphonchop2-creator/mercury-release-control-v2` owns:

- protected-environment provider credentials;
- GitHub repository and ruleset preflight;
- canonical public-tree construction;
- history-free staging publication;
- full Git and hosted-surface secret scans;
- Render deployment and log inspection;
- production Supabase schema and RAG inspection;
- FlowAccount sandbox read validation;
- sanitized attestation production; and
- final tag and GitHub Release publication.

It never imports or executes Mercury source while provider secrets are present.
Mercury source and manifests are treated as untrusted bytes and parsed through
bounded trusted readers.

### Existing Release Control

`natthaphonchop2-creator/mercury-release-control` remains unchanged as v0.2.1
audit evidence. It is not used by v0.2.2 and is not deleted or rewritten.

## Upgradeable Trust Model

Release-control v2 uses two pull-request checks:

1. A normal unprivileged `pull_request` workflow runs candidate tests with
   read-only permissions, no environment, no secrets, and no production access.
2. A base-owned `pull_request_target` guardian checks out the trusted base and
   reads the candidate as data. It verifies the complete file inventory,
   critical-file SHA-256 manifest, workflow permission ceilings, action pins,
   policy schema, forbidden paths, and secret-scan results. It does not import,
   execute, or source candidate files.

Both checks plus one independent approval are required on protected `main`, and
the rules apply to administrators. A merged control commit becomes trusted only
after these gates. Each Mercury release pins one exact trusted control commit;
later control changes cannot affect that release.

The `production-release` environment requires an independent reviewer,
prevent-self-review, no administrator bypass, and protected branches only.
Provider and publication secrets exist only at this environment scope.

## Canonical Public Tree v1

Both repositories implement `PublicTreeV1` independently. The input is the
exact tar stream produced by `git archive <reviewed-sha>`. Every regular file is
normalized to mode `0755` when any executable bit is present and `0644`
otherwise. The digest is SHA-256 over sorted entries using:

```text
<octal-mode><space><path><NUL><sha256-of-file-bytes>
```

The following paths are excluded:

- any path segment equal to `.git`, `.mercury`, `.superpowers`, `__pycache__`,
  `build`, `dist`, or `release-evidence`, case-insensitively;
- any path segment equal to `.env` or beginning with `.env.`,
  case-insensitively; and
- a final filename equal to one of the blocked audit, credential, provider
  payload, provider response, or validation traffic state filenames already
  defined by Mercury's release package.

Archive members must be normalized relative POSIX paths, unique both exactly and
case-insensitively, regular files only, and within bounded member/byte/depth
limits. Symlinks, hard links, devices, duplicate names, traversal, absolute
paths, and unsupported PAX metadata are rejected.

Mercury maintains versioned public-tree test vectors containing source paths,
modes, content digests, inclusion decisions, and the expected aggregate digest.
Release-control v2 copies the fixture bytes during bootstrap and pins their
SHA-256 in its policy. A cross-repository integration test runs both independent
implementations against the exact Mercury candidate archive and requires equal
entry inventory and digest.

## Staging Flow

1. The trusted control workflow verifies that Mercury `main` equals the supplied
   reviewed SHA and that no `v0.2.2` tag or release exists.
2. It clones all declared Mercury refs using a read-only target token and scans
   the full reachable history.
3. It creates `PublicTreeV1` from the exact reviewed SHA without executing any
   Mercury file.
4. It creates a new one-commit repository containing only that filtered tree.
5. It scans the staged filesystem and one-commit Git history.
6. It publishes an annotated immutable staging tag named
   `v0.2.2-rc.<first-12-reviewed-sha>` to
   `natthaphonchop2-creator/mercury-tools-staging`.
7. If the staging tag already exists, the workflow accepts it only when its
   commit tree, one-commit history, annotation, and digest are identical.

The staging ref is an output of trusted control, not a user-supplied prerequisite.
It is recorded in the attestation and cannot be moved. The staging repository
has a tag ruleset that blocks updates and deletion for `v*-rc.*`, including for
administrators.

## Attestation Flow

After staging publication, the trusted control workflow:

1. verifies repository visibility, IDs, branch protections, tag rulesets,
   immutable-release settings, environment policy, and forbidden repo secrets;
2. verifies Render is live on the exact reviewed Mercury SHA and reports version
   `0.2.2`;
3. scans bounded Render build/runtime logs;
4. verifies public MCP initialization, the exact 20 hosted tools, 254 catalog
   actions, read-only Cloud boundaries, and cited FlowAccount/PEAK RAG results;
5. verifies the approved Supabase project ref, migration history, 17-table
   inventory, empty storage bucket inventory, required function definitions,
   append-only validation controls, and reviewed RAG identities;
6. performs the reviewed FlowAccount sandbox read probe without publishing the
   token or response values; and
7. emits a strict sanitized attestation bound to control repository ID, control
   commit, run ID, run attempt, target repository ID, reviewed Mercury SHA,
   staging ref, public-tree digest, manifest hashes, and observed surface
   summaries.

The attestation contains no credentials, raw provider payloads, provider record
IDs, tax IDs, emails, local paths, or unbounded logs.

## Mercury Artifact Flow

The control workflow dispatches Mercury's `release-v0.2.2.yml` on protected
`main`. Mercury verifies that:

- its workflow pin equals the attestation producer commit;
- origin `main`, the reviewed SHA, Render deployment SHA, and attested SHA agree;
- the attestation artifact ID, digest, payload digest, run, attempt, repository
  ID, staging ref, and public-tree digest agree;
- the staging ref contains exactly one unrelated commit with the same canonical
  tree; and
- no release tag or GitHub Release exists yet.

Mercury then builds wheel, sdist, plugin archive, and source archive in the
pinned Linux/amd64 toolchain with networking disabled and no secrets. It scans
the artifacts, performs a clean plugin install, and emits a bounded
`release-ready` handoff. It cannot create tags or releases.

## Publication Flow

The trusted publisher consumes the exact release-ready handoff and independently
re-verifies the original control attestation and Mercury artifact metadata. It
rebuilds the canonical source from the reviewed Git objects, compares artifact
digests, verifies the existing Render deployment, and then:

1. creates the annotated tag `v0.2.2` on the reviewed Mercury SHA;
2. verifies the peeled tag commit before any release upload;
3. creates a draft GitHub Release, uploads all verified assets, digest manifest,
   sanitized attestation, and release notes, then downloads and verifies every
   draft asset;
4. publishes the verified draft, enables immutable release state, and verifies
   the final asset identities; and
5. runs anonymous clone, marketplace discovery, one-MCP/19-local-tool startup,
   hosted MCP, and judge quickstart smoke tests.

If an existing tag, release, or asset differs, publication stops and the next
version is required. The workflow never force-pushes, moves a tag, overwrites an
asset, or republishes different bytes under the same version.

## Version and Product Changes

Mercury changes only release-facing product metadata and release architecture:

- package version becomes `0.2.2`;
- plugin and marketplace versions become `0.2.2`;
- the local plugin launcher pins immutable `v0.2.2`;
- Render status reports `0.2.2` and the exact deployment commit;
- release workflows, notes, policies, tests, and documentation target v0.2.2;
- the independent-project/non-affiliation notice remains unchanged; and
- ERP catalog identities, accounting Skills, local credential policy, action
  risk tiers, and production write controls remain unchanged.

The public marketplace on `main` may reference `v0.2.2` briefly before the tag
is published. The v0.2.1 tag remains directly installable during this bounded
release window. The final control workflow should be ready, reviewed, and fully
configured before the Mercury version PR is merged so this window is minimized.

## Required Secrets and Variables

The release-control `production-release` environment contains the minimum
provider and publication credentials required by the approved inspector. The
current known manual prerequisites are:

- a valid `RENDER_API_TOKEN` obtained through Render login or an API key; and
- `SUPABASE_DB_URL` for the approved project, entered directly into GitHub's
  environment secret UI or through a local stdin-safe command.

Secret values must not be pasted into chat, command arguments, shell history,
GitHub repository secrets, Mercury environment scope, or tracked files. Any
credential previously exposed outside an approved secret store is rotated
before release. FlowAccount sandbox and GitHub operation credentials are entered
directly into the protected environment through the GitHub UI or an stdin-safe
local command and are verified by name/presence only.

## Failure Handling

- Missing reviewer, secret, variable, protection, provider access, or database
  access blocks attestation before Mercury is dispatched.
- Staging creation is idempotent only for an identical one-commit tree and
  annotated ref.
- Render or Supabase mismatch blocks attestation; it does not create a partial
  release.
- Artifact build or scan failure leaves only short-lived Actions artifacts and
  no release tag.
- A target workflow run is accepted only when its head SHA equals the reviewed
  Mercury SHA and its path is the pinned v0.2.2 workflow.
- A post-tag discrepancy is handled as a new version and never by moving the
  immutable tag.
- Production ERP mutations remain forbidden in release automation.

## Testing Strategy

### Unit Tests

- both public-tree implementations accept and reject the same versioned path,
  mode, archive, and duplicate-name vectors;
- full and filtered archives cannot be confused;
- control manifests cover every executable and workflow file by SHA-256;
- privileged PR guardian code never imports or executes candidate files;
- workflow pins reject zero, branch names, short SHAs, and mismatched repo IDs;
- attestation and handoff schemas reject unknown keys and unbounded values;
- tag/release publication rejects pre-existing mismatched objects; and
- redaction rejects tokens, API keys, emails, tax IDs, local paths, and raw
  provider payloads.

### Cross-Repository Integration Tests

- control v2 builds a filtered staging snapshot from the exact Mercury archive;
- Mercury independently computes the same entry inventory and digest for the
  reviewed candidate fixture;
- the staging repo has one unrelated commit and an annotated immutable ref;
- sanitized control attestation is accepted by Mercury and altered identity
  fields are rejected;
- Mercury release-ready handoff is accepted by the trusted publisher and altered
  artifact metadata is rejected; and
- no provider secret is available in candidate containers.

The exact entry count is recorded with each reviewed fixture and attestation but
is not hard-coded across releases. The canonical digest, inclusion rules, and
per-candidate inventory are the authoritative contract as the repository
evolves.

### Remote Acceptance

- both repositories are public and protected before privileged runs;
- independent review is required and administrator bypass is disabled;
- Render reports version `0.2.2` and the reviewed commit;
- Supabase exact-policy inspection passes;
- FlowAccount sandbox read probe passes without value disclosure;
- public staging passes anonymous installation;
- release artifacts and source are reproducible under the pinned toolchain;
- GitHub Release `v0.2.2` is immutable and points to the reviewed main commit;
- anonymous Codex installation exposes one `mercury-finance` MCP and 19 local
  tools; and
- hosted MCP exposes 20 tools and 254 catalog actions with cited RAG context.

## Release Sequence

1. Implement and test release-control v2 locally without provider secrets.
2. Create the public release-control v2 repository and configure protections.
3. Configure its protected environment and migrate secret values through safe
   local input paths.
4. Review and merge release-control v2; record its exact trusted commit.
5. Update Mercury to v0.2.2 and pin that exact control commit.
6. Run cross-repository, full test, secret history, and artifact tests on the
   Mercury PR.
7. Merge the exact reviewed Mercury PR and deploy that commit to Render.
8. Run trusted control attestation, which creates and verifies staging.
9. Run the secretless Mercury artifact workflow.
10. Run the trusted publisher to create tag and Release last.
11. Run anonymous public installation and hosted MCP verification.

No step may be reordered in a way that creates the final tag before the trusted
attestation, staging, artifact, and publication preconditions pass.
