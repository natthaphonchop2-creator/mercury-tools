# Mercury v0.2.1 Public Endpoint Validation Design

**Date:** 2026-07-13

**Status:** Approved design, pending written-spec review

**Target branch:** `mercury-v0.2.1-public` from `origin/main`

**Target release:** `v0.2.1`

## Final-Review Security Amendment (2026-07-16)

The final release boundary supersedes any workflow detail below that would run
candidate code with hosted-provider or production credentials. A separately
reviewed and immutable release-control repository owns GitHub, marketplace,
Render, public MCP, FlowAccount, and production Supabase inspection. Mercury
receives only a strict sanitized, SHA/run/attempt-bound attestation and builds
inside secretless, networkless, read-only candidate containers.

The release-control repository must be public, branch-protected, and have its
administratively created `production-release` environment pass the remote
preflight before its implementation SHA is pinned. Production Supabase state
is exact-policy-bound to the approved project ref, migration `20260716100000`,
canonical inventory, migration history digest, and function/schema digests.
After production/provider secrets are removed, Mercury must be made public and
its `main` protected before selecting the final reviewed SHA. Public visibility
therefore precedes the trusted release run, while tag and asset publication
remain last. The copyable contract and full sequencing are in
`release-control/README.md`.

## Summary

Mercury v0.2.1 will turn the existing immutable ERP action catalog into an
evidence-bearing, human-readable API knowledge layer that a host LLM can use to
plan and execute accounting work. Every cataloged FlowAccount action will
receive a qualification record. A live sandbox request is issued only when the
exact action version appears in a reviewed sandbox-execution manifest;
remaining actions receive truthful blocked or contract-only results. PEAK
receives documented-schema contract validation without a claim of provider
conformance. The release also adds accounting semantics, cross-MCP handoff
contracts, and sanitized validation knowledge for Mercury MCP retrieval.

The release will also include the RAG batching hotfix already present on
`origin/main`, move the plugin launcher from `v0.2.0` to the immutable
`v0.2.1` tag, scan the declared Git and hosted public-exposure corpus plus
release artifacts for secrets, verify a clean marketplace installation, and
publish the tag/assets only after every pre-public release gate passes.

Sandbox credentials supplied out of band are test inputs, not product data.
They must never be committed, logged, uploaded to Supabase or Render, embedded
in release artifacts, or printed in test output.

## Goals

1. Account for all 254 current catalog actions:
   - 190 FlowAccount actions receive a qualification result; reviewed
     `sandbox_executable` action versions receive a live sandbox attempt.
   - 64 PEAK actions receive frozen-catalog and documented-schema contract
     checks until PEAK test credentials are available.
2. Record a truthful validation outcome for every action without claiming that
   blocked or contract-only actions passed live validation.
3. Store sanitized, human-readable Thai and English explanations that a host
   LLM can retrieve through Mercury MCP.
4. Add semantic contracts that explain how endpoint outputs participate in
   accounting workflows and how actions connect to one another.
5. Add cross-MCP orchestration contracts for Google Drive, Google Sheets,
   Gmail, and other user-connected tools while preserving credential and
   approval boundaries.
6. Publish `v0.2.1` from the reviewed GitHub `main` commit and make the release
   reproducibly installable from the Codex plugin marketplace.
7. Produce a scoped, fail-closed attestation that the declared public-exposure
   corpus passed independent secret scans and contains no detected operator API
   key, password, token, credential file, or secret value.

## Non-Goals

- Mercury does not become a bank, payment processor, or custodian of funds.
- Mercury does not store ERP or Google credentials in Cloud services.
- Mercury MCP does not directly invoke unrelated MCP servers. The host agent
  orchestrates Mercury and other MCP servers.
- PEAK actions are not described as live-validated without PEAK test
  credentials.
- The validation runner does not send production email, initiate production
  payments, or mutate production accounting records.
- A failed or blocked endpoint is not hidden to improve a coverage percentage.

### Release Inventory Freeze

The release matrix is generated from a frozen Git commit, source hash set, and
catalog manifest. The current expected count is 254, but that number is not
hard-coded into the runner. If source import changes the inventory, the run
stops until the manifest, expected counts, documentation, and acceptance report
are regenerated from the same reviewed commit. The final report selects one
terminal qualification result per frozen action version; lower-level attempts
and observations may contain multiple append-only records.

## Architectural Decisions

### One Public Plugin, One Local MCP, One Read-Only Cloud Brain

The installed Codex plugin continues to expose exactly one local stdio MCP
server. Local execution owns ERP credentials, request previews, confirmations,
network access, and the local audit ledger. Render and Supabase provide
sanitized catalog, validation knowledge, accounting knowledge, and RAG only.

No Cloud component receives ERP credentials or raw ERP payloads.

### Host-Orchestrated Cross-MCP Workflows

Codex or another host LLM coordinates tools from multiple MCP servers:

```text
User
  -> Host LLM
      -> Mercury MCP: ERP actions and accounting semantics
      -> Google Drive MCP: files and statements
      -> Google Sheets MCP: tabular inputs and reports
      -> Gmail MCP: settlement messages and approval-gated drafts
      -> Other MCPs: banks, commerce platforms, calendar, or messaging
```

Mercury returns structured handoff data and an ordered plan. It never receives
Google OAuth tokens, and Google tools never receive ERP client secrets.
Every handoff treats content from email, files, spreadsheets, ERP responses,
and other MCP servers as untrusted data rather than instructions.

## Endpoint Qualification Model

### Validation Status

Each action receives one public validation status independent of the existing
low-level `observed_state`:

| Status | Meaning |
| --- | --- |
| `live_success` | A sanitized sandbox request completed with the expected outcome. |
| `live_failed` | A sandbox request completed with a classified failure. |
| `contract_validated` | Schema, method, path, auth shape, and policy passed without a live mutation. |
| `blocked_missing_credentials` | The connector cannot be called because test credentials are unavailable. |
| `blocked_missing_prerequisite` | Required fixture data or an upstream identifier could not be created. |
| `blocked_external_effect` | The action could send email, share data, pay, invite, or affect an uncontrolled target. |
| `unsupported_by_sandbox` | The documented action is unavailable in the sandbox environment. |
| `outcome_unknown` | The request may have reached the provider but the final state is not provable. |

Every catalog action must appear exactly once in the final coverage report.

### Evidence Level

Validation status and evidence level are separate fields:

| Evidence level | Meaning |
| --- | --- |
| `documented` | The provider document explicitly defines the behavior. |
| `contract_validated` | Mercury validated the local schema and request construction. |
| `sandbox_observed` | A sandbox request produced a sanitized, attributable result. |
| `accountant_reviewed` | An accountant reviewed the accounting meaning or workflow use. |

Success rules, error rules, idempotency behavior, and accounting semantics are
promoted into the reviewed catalog only when their evidence level is recorded.
One successful call or one provider error is not sufficient to infer a general
provider guarantee.

### Semantic Contract

Each action gains a sanitized semantic contract:

```json
{
  "business_object": "invoice",
  "operation": "list",
  "accounting_uses": [
    "accounts_receivable_reconciliation",
    "revenue_review",
    "vat_output_review"
  ],
  "output_semantics": {
    "document_id": "Identifier for a later document lookup",
    "document_date": "Accounting document date",
    "reference": "External or document reference used for matching",
    "total_amount": "Gross document amount",
    "vat_amount": "VAT amount",
    "status": "Provider document state"
  },
  "join_keys": ["document_id", "reference", "total_amount"],
  "next_action_ids": [],
  "required_external_capabilities": [],
  "optional_external_capabilities": [],
  "fallbacks": []
}
```

Semantic contracts contain field meanings and workflow relationships, never
field values from a real response.

Accounting uses and join keys are deterministic reviewed metadata. They are
not generated at runtime by an LLM from a provider payload. LLMs may use the
contract to plan work, but they cannot silently change the contract.

### Human Validation Knowledge

A new immutable validation-knowledge record is keyed by connector, action ID,
version ID, environment, and test run. It contains:

- validation status;
- Thai and English summaries;
- execution eligibility: `discovery_only`, `sandbox_read`,
  `sandbox_write_with_approval`, `production_pending_validation`, or `blocked`;
- evaluation time and optional expiry;
- prerequisites and upstream action IDs;
- limitations and a recommended next step;
- HTTP status class and latency;
- sanitized response field/type shape;
- test environment and timestamp;
- an opaque evidence ID and evidence hash;
- reviewer and runner version.

The record must not contain request payloads, response values, document IDs,
tax IDs, names, email addresses, passwords, tokens, API keys, repository paths,
or provider credential identifiers.

Thai and English summaries are generated from deterministic status templates
and reviewed semantic metadata. Raw provider responses are sanitized before
the template layer and are never sent to an LLM merely to produce validation
copy.

## Data Model

### `erp_action_validation_knowledge`

Add a Supabase table dedicated to public validation knowledge. The table uses
RLS, grants write access only to `service_role`, and exposes no direct
`anon`/`authenticated` table privileges. Public access continues through the
strict Mercury Cloud response model.

Rows are append-only. A database trigger rejects update and delete operations,
and `(connector_id, action_id, version_id, environment, run_id)` is unique. The
service-role key exists only in the Cloud backend. Cloud reads return only rows
marked `approved_public` through an allowlisted response DTO; negative tests
prove that `anon` and `authenticated` roles have no direct table access.

Required columns:

- `id uuid primary key`;
- `opaque_evidence_id text unique`;
- `run_id text` containing a non-secret opaque run identifier;
- `action_id text` and `version_id text` referencing immutable versions;
- `connector_id text`;
- `environment text`;
- `validation_status text` constrained to the status taxonomy;
- `evidence_level text` constrained to the evidence taxonomy;
- `execution_eligibility text` constrained to the eligibility taxonomy;
- `approved_public boolean not null default false`;
- `summary_th text` and `summary_en text`;
- `prerequisites jsonb` containing sanitized labels and action IDs only;
- `limitations jsonb` containing sanitized strings only;
- `recommended_next_step text`;
- `response_shape jsonb` containing field names and type names only;
- `status_class text`;
- `latency_ms integer`;
- `semantic_contract jsonb`;
- `evidence_sha256 text`;
- `reviewed_by text` using a role label rather than a personal email;
- `evaluated_at timestamptz` and nullable `expires_at timestamptz`;
- `created_at timestamptz`.

The migration rejects credential-like keys recursively and adds indexes for
active action lookup, connector/status reporting, and newest evidence lookup.
Public records are built only from typed allowlisted fields and controlled
summary templates. Raw provider strings, custom labels, request payloads, and
response values are not valid publisher inputs. Pattern redaction and secret
scanning are defense in depth; an unclassified field fails publication.

### Existing Observations

`erp_action_observations` remains the compact machine observation stream. A
successful or failed live call writes one sanitized observation. Blocked and
contract-only results are represented in validation knowledge without
inventing a provider response.

### RAG Publication

The validation publisher produces reviewed connector knowledge documents
grouped by capability and action. Documents include action IDs in metadata and
are ingested through the existing bounded Supabase chunk upload path. RAG
documents contain the human summaries, prerequisites, limitations, semantic
contracts, opaque evidence IDs, and evidence hashes, not raw test traffic.
Internal evidence resolution is separate and never exposes a filesystem path,
provider identifier, raw traffic URI, or repository location.

Only provider documentation that is public or explicitly redistributable may
be included verbatim. Restricted provider documents remain local inputs;
public artifacts contain derived action metadata, short factual descriptions,
and source links rather than copied documentation bodies.

## FlowAccount Sandbox Validation Runner

### Credential Handling

The operator-provided sandbox credentials are loaded through the existing
interactive repository credential setup. Secret values are entered through
stdin, never command arguments. The generated `.mercury` state is ignored by
Git, stays in the isolated validation worktree, and is cleared after the run.

Before any authentication request, the runner validates the configured origins
against a compile-time HTTPS allowlist for FlowAccount sandbox API and token
hosts. The HTTP transport rejects redirects, production hostnames, embedded
credentials, unexpected ports, and TLS hostname mismatch. Credentials may be
submitted only after these checks pass. A subsequent safe company probe must
confirm the expected sandbox tenant before an action request is eligible.

The sandbox website account is not used unless an API-only prerequisite cannot
be inspected or confirmed. Browser automation must not save the password and
must not copy it into logs or artifacts.

### Run Isolation

Every run creates an opaque run ID and a visible fixture prefix:

```text
MERCURY-V021-<run-id>
```

The fixture registry records only test-created object relationships in the
local ignored artifact directory. Provider IDs are held in memory or encrypted
local state and are removed from the public report.

Each action version has a reviewed sandbox-execution manifest. The manifest
declares whether an HTTP call is permitted, fixture ownership predicates,
required preconditions, the approved fixture builder, the cleanup method,
external effects, maximum attempts, and request budget. An action absent from
this manifest is contract-only and cannot be executed live.

### Attempt Policy

1. Validate sandbox API and token origins before transmitting credentials.
2. Authenticate with redirects disabled and verify the sandbox tenant through
   the safe company probe.
3. Freeze the reviewed sandbox-execution manifest and traverse eligible actions
   in dependency order.
4. Execute eligible GET actions with bounded pagination and sanitized result-shape
   capture.
5. Execute eligible POST actions using deterministic test fixtures and the
   action-specific request budget.
6. Execute eligible PUT or PATCH only when the manifest proves fixture
   ownership and defines cleanup.
7. Execute eligible DELETE or void only when the manifest proves fixture
   ownership, the provider contract makes the target unambiguous, and cleanup
   verification is defined.
8. Block email, share, invite, payment, or uncontrolled external effects unless
   a reviewed manifest proves provider sandbox isolation and a controlled
   destination. Provider sandbox branding alone is not sufficient proof.
9. Never retry an `outcome_unknown` mutation.
10. Reconcile fixture state and clean up in reverse dependency order.

Rate limits, pagination, retryable reads, non-retryable writes, and provider
error classes are explicit runner policies. The runner uses a low request rate
and stops on authentication-host drift or production-host detection.

### Dependency Planning

The planner builds a directed action graph from:

- path and body identifiers;
- documented prerequisites;
- response field/type shapes;
- explicit preflight action IDs;
- semantic business-object relationships.

Inferred dependencies create recommendations only. They never authorize a
write. Live execution requires the reviewed action-version manifest, ownership
predicate, preconditions, fixture builder, and cleanup method.

When a prerequisite cannot be satisfied, the action is still represented in
the report as `blocked_missing_prerequisite` with a Thai explanation and the
required upstream action.

An unknown mutation or cleanup failure changes the run state to `quarantined`,
blocks dependent actions and public promotion, and requires verified cleanup or
an explicitly reviewed documented exception before release.

## PEAK Validation

All PEAK actions receive documented-schema contract checks:

- action identity and version verification;
- method/path/environment validation;
- request schema and required-field validation;
- risk, confirmation, and external-effect classification;
- semantic contract and accounting-use mapping;
- dependency and fallback mapping;
- generated request-shape contract tests;
- human-readable `blocked_missing_credentials` validation knowledge.

For PEAK, `contract_validated` means conformance to the frozen Mercury catalog
and cited documented schema only. It is not provider conformance, a successful
UAT call, or evidence that the provider currently supports the operation.

The runner can resume PEAK live qualification later without rebuilding the
catalog. No PEAK action is marked `live_success` until a successful UAT call is
observed.

## Accounting Workflow Templates

v0.2.1 adds reusable host-agent workflow templates for:

- accounts receivable reconciliation;
- accounts payable reconciliation;
- bank or settlement reconciliation;
- invoice and receipt review;
- VAT output/input review;
- marketplace settlement review;
- month-end evidence gathering;
- management reporting.

### Reconciliation Example

For a request such as "ช่วยทำ Flow กระทบยอด", the host:

1. checks the connected Mercury and external MCP capabilities;
2. asks for the reconciliation scope and period only when missing;
3. obtains settlement files through Gmail, Drive, Sheets, or file upload;
4. uses Mercury semantic contracts to choose invoices, receipts, payments,
   credit notes, and related ERP actions;
5. normalizes inputs into a canonical transaction handoff schema;
6. matches amount, date, reference, counterparty key, and document state;
7. reports matched, unmatched, duplicate, and difference groups;
8. creates write previews for approved adjustments;
9. executes a write only after Mercury confirmation gates pass;
10. optionally creates a Google Sheets report or Gmail draft through the
    corresponding user-connected MCP.

If the ERP API does not expose bank transactions, the workflow explicitly
requests a bank statement or bank MCP instead of inferring missing data.

## Cross-MCP Orchestration Contract

Workflow and Skill metadata gains:

- `required_capabilities`;
- `optional_capabilities`;
- `handoff_schema`;
- `fallbacks`;
- `approval_points`;
- `evidence_requirements`;
- `blocked_actions`;
- `source` and `destination` connector IDs;
- `purpose` and `data_classification`;
- `allowed_fields` and `redaction_policy`;
- `retention_limit`;
- `content_is_untrusted: true`.

The host validates capability availability before starting a step. Missing
Google tools produce a connect-or-upload fallback. Mercury ERP writes, Google
Sheets writes, Gmail draft creation, Gmail send, file sharing, and deletions
retain separate approvals.

Handoff content is data only and cannot supply instructions, tool names,
destinations, or approval state. Each approval is single-use, expires, and is
bound to the exact action version, destination, side effect, allowed-field
schema, and payload digest. If the destination MCP cannot enforce the required
boundary, the handoff step is blocked.

## MCP Surface Changes

The existing 19-tool local MCP remains stable. Responses are extended without
adding a second server:

- `search_erp_actions` includes validation status, execution eligibility,
  evidence level, human summary, accounting uses, and ambiguity.
- `get_erp_action_schema` includes the semantic contract, prerequisites,
  limitations, next actions, and deterministic approved validation evidence.
- `retrieve_context_pack` can retrieve endpoint validation knowledge by
  connector, capability, accounting use, and action ID.
- `run_accounting_skill` returns required external capabilities, handoff
  schemas, fallbacks, and approval points.
- `connector_status` reports catalog and validation coverage without exposing
  credential values.

Evidence selection requires an exact action version and environment, then
chooses the latest approved, unexpired run while returning every current
blocking condition. A later failed or quarantined run cannot be hidden by an
older success, and a raw "newest record" query is not an eligibility decision.

No new endpoint tool accepts raw API URLs or arbitrary unreviewed hosts.

## Secret and Privacy Controls

### Runtime Controls

- Secret input uses interactive stdin only.
- Secret values never appear in CLI arguments, exceptions, snapshots, audit
  events, validation records, RAG chunks, fixtures, or reports.
- Known credential fingerprints are checked before every artifact write.
- Redaction covers bearer tokens, client secrets, API keys, passwords, emails,
  tax IDs, document IDs, and long high-entropy strings.
- Validation artifacts default to an ignored directory and are sanitized before
  promotion into tracked documentation.
- Public knowledge accepts only typed allowlisted fields. Free-form provider
  strings, custom labels, evidence paths, and raw identifiers are rejected
  before publication rather than relying on redaction to repair them.

### Public Release Secret Gate

Before repository visibility changes, the release process enumerates a declared
public-exposure corpus and scans every accessible surface. The corpus includes
all explicitly fetched remote refs, branches and tags; GitHub pull-request refs;
release assets; Actions logs, artifacts, and caches; packages; Pages; wiki;
marketplace copies; Render build and runtime logs; and Supabase knowledge or
storage used by the product. Any surface that cannot be inspected or proven
inaccessible blocks public visibility.

The following checks run against a fresh clone and the declared corpus:

1. exact known-credential fingerprint search over every ref and tag;
2. Gitleaks history scan over `--all`;
3. TruffleHog Git history scan;
4. filesystem scan of the release checkout;
5. reachable object and blob inventory scan plus explicit hosted pull-request
   ref coverage;
6. generated wheel, source archive, plugin sparse checkout, and GitHub release
   archive scan;
7. forbidden path scan for `.env`, `.mercury`, credential stores, test
   artifacts, audit ledgers, and downloaded provider payloads;
8. entropy and provider-token pattern scan;
9. manual review of findings and allowlist entries.

Allowlist entries must identify a non-secret test fixture or documentation
placeholder. A finding that cannot be proven safe blocks the release.

If any real credential appears in reachable history, the repository must remain
private, the credential must be rotated, and the public repository must be
produced from a verified clean history before continuing.

CI adds a repeatable secret scan for pull requests and the release workflow.
The release report attests only that the named scans passed over the declared
corpus. It does not claim mathematical proof that a secret cannot exist outside
that corpus.

The public README and plugin metadata state that this independent open-source
project is not affiliated with Mercury Technologies, Inc. Public code release
does not replace a trademark and product-name review before commercial launch.

## Release Process

1. Develop on `mercury-v0.2.1-public`, based on current `origin/main`.
2. Add endpoint qualification, semantic, cross-MCP, and security changes using
   test-driven implementation.
3. Run the FlowAccount sandbox matrix and produce sanitized coverage artifacts.
4. Apply and verify the Supabase migration and publish sanitized knowledge.
5. Update plugin metadata and the future immutable launcher reference to
   `v0.2.1` in the reviewed release candidate.
6. Run Ruff, the full test suite, integration tests, MCP smoke tests, catalog
   validation, and clean-wheel installation.
7. Reproducibly build the wheel, source archive, plugin bundle, and repository
   archive from the candidate commit; scan them and record SHA-256 digests.
8. Run the full declared-corpus secret gate against a fresh remote clone.
9. Validate unauthenticated clone, marketplace discovery, and plugin install
   against a separate public staging repository containing only the scanned
   release-candidate snapshot and no private history.
10. Open and review a pull request into `main`.
11. Merge only after CI, sandbox, migration, artifact, staging, and security
    gates pass.
12. Rebuild candidate artifacts from the exact reviewed `main` commit, verify
    their digests or reproducible content tree, and repeat the secret gate.
13. Create annotated tag `v0.2.1` on that exact `main` commit and push it once.
14. Verify the tag tree and uploaded release assets match the reviewed commit
    and recorded artifact digests.
15. Install the marketplace plugin from `v0.2.1` in an isolated `CODEX_HOME` and
    verify one `mercury-finance` MCP with the expected tool surface.
16. Deploy the same reviewed `main` commit to Render and verify health, RAG,
    catalog, read-only Cloud boundaries, and deployment-log secret scans.
17. Change the primary GitHub repository visibility to public only after every
    pre-public gate passes.
18. Perform post-change unauthenticated clone, marketplace, plugin, and judge
    quickstart verification from another clean environment.

The public release must not move or recreate an existing tag. A post-tag
discrepancy blocks release publication and primary-repository visibility;
remediation uses a new version. A post-public failure is treated as a security
incident with containment and credential rotation, not as a reversible gate.

## Testing Strategy

### Unit Tests

- validation status and semantic-contract models reject unknown keys and secret
  values;
- response-shape extraction stores field/type metadata but no values;
- fixture names and IDs cannot leak into public knowledge;
- dependency planning is deterministic and cycle-safe;
- unsafe effects cannot execute without sandbox confinement;
- mutation retries are rejected after an unknown outcome;
- cross-MCP contracts validate capability, handoff, fallback, and approval
  metadata;
- MCP responses remain strict and backward-compatible;
- secret scanners fail closed when unavailable or when findings exist.

### Integration Tests

- Supabase migration creates protected validation-knowledge tables and indexes;
- published validation knowledge can be retrieved by action and accounting use;
- RAG returns Thai endpoint explanations with citations;
- local MCP merges catalog, semantic, and validation knowledge;
- FlowAccount auth and safe company probe use sandbox hosts only;
- representative fixture dependency chains cover read, create, update, and
  cleanup behavior;
- PEAK produces contract-only knowledge without false live evidence.

### Acceptance Tests

- the frozen manifest count equals the coverage manifest count, and each
  `(action_id, version_id)` appears exactly once in the terminal report;
- every FlowAccount action has either an HTTP attempt authorized by the reviewed
  execution manifest or an explicit blocked/contract-only result;
- no PEAK action is marked live without evidence;
- a deterministic reconciliation fixture produces the expected action sequence,
  canonical match groups, approval points, and allowed-field handoff schemas for
  Mercury plus Sheets/Drive/Gmail capabilities;
- controlled Thai and English status templates cover every terminal status and
  reference immutable action IDs without provider values;
- the declared public-exposure corpus passes every named secret scan with no
  unresolved finding and no raw provider value in public MCP output;
- clean marketplace installation from `v0.2.1` exposes one local MCP;
- the GitHub repository is publicly cloneable only after every gate passes.

The release report records the pinned environment, exact command, exit code,
coverage manifest hash, and artifact digest for every gate. At minimum it runs:

```text
uv run ruff check .
uv run pytest -q
uv run mercury doctor --repo-root .
uv run mercury catalog qualify --connector flowaccount --env sandbox --all
uv run mercury catalog validate --connector peak --all
uv run mercury release scan-secrets --all-history --artifacts dist
uv run mercury release verify --version 0.2.1
```

No security, migration, MCP, release, or required live-sandbox test may be
skipped. Any other allowed skip requires a named test ID, written rationale,
owner role, expiry, and explicit release approval. The current clean-wheel
network timeout and baseline integration skips must be resolved or explicitly
reclassified before release; they cannot be silently accepted.

## Failure Handling and Rollback

- Authentication-host mismatch stops the entire live run before any mutation.
- A production hostname stops the sandbox runner immediately.
- Rate-limit failures pause read work and block mutation retries.
- Unknown mutation outcomes are reconciled through status reads and never
  blindly repeated.
- Cleanup failures quarantine the run, block dependent actions and public
  promotion, and require verified cleanup or an explicitly approved exception;
  public reports never expose provider identifiers.
- Supabase publication is idempotent by evidence and action version.
- A failed pre-tag security gate leaves the repository private and prevents
  tagging. A post-tag discrepancy keeps the primary repository private and
  requires a new version rather than moving the tag.
- A failed clean installation prevents release publication.
- Render remains on the last known-good commit until the reviewed main commit
  passes health and smoke checks.

## Acceptance Decision

Mercury v0.2.1 is ready for public use only when:

1. all 254 actions have truthful qualification records;
2. FlowAccount sandbox evidence and PEAK contract evidence are published in a
   sanitized, human-readable form;
3. accounting semantics and cross-MCP workflows are retrievable through the
   existing MCP surface;
4. the full automated and clean-install test suite passes;
5. the declared public-exposure corpus and every release artifact pass the
   named independent secret scans with no unresolved finding;
6. the exact reviewed main commit is tagged, deployed, and clean-installed;
7. the repository can be made public without exposing operator credentials or
   private business data.
